SMS L1 — ENTREGA TÉCNICA

ALCANCE
Código fuente de backend, frontend, migraciones, catálogos base y pruebas.
No incluye bases de datos, usuarios locales, contraseñas, claves de proveedores,
adjuntos, respaldos, logs ni archivos usados en las demostraciones.
Los reportantes públicos no necesitan una cuenta; la consulta se vincula al
navegador que registró el reporte mediante cookies de acceso.

ESTRUCTURA Y REQUISITOS
backend/: Node.js, Express, TypeScript, Prisma y PostgreSQL.
frontend/: React, Vite y TypeScript. La compilación genera archivos estáticos.
Referencia de las imágenes incluidas: Node 22 y PostgreSQL 16.
Los package-lock.json fijan las dependencias; instalar con npm ci.
docker-compose.yml es para desarrollo con Mailpit (no entrega correo real).
docker-compose.production.yml prepara una instalación administrada por TI.
ENTREGA-TI.txt es esta guía. No se incluyen los informes locales en Markdown.

CONFIGURACIÓN
Crear los archivos privados a partir de los ejemplos, sin versionarlos:
  backend/.env.example -> backend/.env (instalación sin contenedores)
  frontend/.env.example -> frontend/.env (compilación sin contenedores)
  .env.production.example -> .env.production (Docker de producción)
Generar secretos distintos para PostgreSQL y JWT. El ejemplo Docker espera una
contraseña PostgreSQL hexadecimal; otros caracteres requieren codificación URL.
Usar un gestor de secretos para los valores definitivos.

Google: configurar un cliente OAuth Web de la empresa, autorizar el origen HTTPS
definitivo y usar el mismo ID en GOOGLE_CLIENT_ID y VITE_GOOGLE_CLIENT_ID.
Google permite entrar a usuarios ya registrados y activos; no crea cuentas.
Correo: elegir Resend con dominio verificado o SMTP de la empresa. Si SMTP_HOST
está definido, tiene prioridad sobre Resend. Puerto 465 usa SMTP_SECURE=true;
587 utiliza STARTTLS para SMTP autenticado. Gmail requiere contraseña de aplicación.
Push: crear claves VAPID propias y hacer coincidir VAPID_PUBLIC_KEY y
VITE_VAPID_PUBLIC_KEY. El navegador necesita HTTPS y autorización del usuario.
Las variables VITE_* son públicas y se incorporan al compilar el frontend;
cambiar OAuth o la clave pública push exige reconstruirlo.
Configurar FRONTEND_URL y TRUST_PROXY_HOPS según la URL y cadena real de proxies.

ADMINISTRADOR INICIAL
No hay contraseña predeterminada ni cuentas de demostración en la inicialización.
setup:catalogs / npm run seed solo preparan catálogos, áreas y roles.
Para crear el primer administrador, desde backend/ en PowerShell:
  $env:INITIAL_ADMIN_EMAIL = 'administrador@empresa.example'
  $env:INITIAL_ADMIN_NAME = 'Administrador de la empresa'
  $adminSecret = Read-Host 'Contraseña temporal (mínimo 16 caracteres)' -AsSecureString
  $env:INITIAL_ADMIN_PASSWORD = [System.Net.NetworkCredential]::new('', $adminSecret).Password
  npm run setup:admin
  Remove-Item Env:INITIAL_ADMIN_PASSWORD
El primer acceso exige cambiar la contraseña. El comando rechaza cuentas
existentes y no funciona si ya hay un administrador; no sirve para restablecerlo.
El administrador crea los demás usuarios mediante la gestión normal de la web.
No puede desactivarse ni retirarse su propio rol; otro administrador debe tramitar
ese cambio. Mantener una cuenta administrativa de respaldo bajo custodia de TI.
Para la baja o cambio de rol/área de un jefe con pendientes, primero abrir Editar
usuario > Reasignar planes pendientes. Elegir un jefe activo del área de cada
plan y registrar un motivo. La transferencia conserva estados, avances, plazos,
evidencias y actividades terminadas, notifica a los reemplazos y deja auditoría.
Después guardar la desactivación o el cambio del usuario. Si cambia la lista de
planes durante la revisión, actualizarla antes de confirmar; no reenviar a ciegas.

PRIMERA INSTALACIÓN CON DOCKER (BASE VACÍA)
Desde la raíz, completar primero .env.production:
  docker compose --env-file .env.production -f docker-compose.production.yml build
  docker compose --env-file .env.production -f docker-compose.production.yml up -d postgres
  docker compose --env-file .env.production -f docker-compose.production.yml run --rm schema
  docker compose --env-file .env.production -f docker-compose.production.yml run --rm --no-deps backend npm run setup:catalogs
Para el administrador, definir INITIAL_ADMIN_EMAIL, INITIAL_ADMIN_NAME e
INITIAL_ADMIN_PASSWORD de forma privada en el entorno, como en el ejemplo anterior:
  docker compose --env-file .env.production -f docker-compose.production.yml run --rm --no-deps -e INITIAL_ADMIN_EMAIL -e INITIAL_ADMIN_NAME -e INITIAL_ADMIN_PASSWORD backend npm run setup:admin
  Remove-Item Env:INITIAL_ADMIN_PASSWORD
  docker compose --env-file .env.production -f docker-compose.production.yml up -d backend frontend
  docker compose --env-file .env.production -f docker-compose.production.yml ps
Publicar el frontend detrás del HTTPS de la empresa. PostgreSQL y backend se
mantienen en la red interna del compose. No usar el servidor Vite de desarrollo.

BASES EXISTENTES Y ACTUALIZACIONES
No ejecutar migrate reset, db push, seeds antiguos ni eliminar volúmenes.
Antes de migrar una base existente, revisar su historial con prisma migrate status
y comparar su esquema. Si fue creada fuera de migraciones, TI debe reconciliar
la línea base antes de migrate deploy. Aplicar todas las migraciones versionadas
en backend/prisma/migrations, incluyendo importacion_locks y user_import_profile.
No depender de un número fijo de migraciones: cambia con cada versión.
Respaldar base y adjuntos antes de actualizar, y probar la restauración.
En Render u otro alojamiento, aplicar las migraciones antes de activar el nuevo
backend: desde backend/, con las variables privadas de ese entorno, ejecutar
npx prisma migrate deploy y comprobar npx prisma migrate status. El Dockerfile
solo inicia el servidor; no aplica migraciones automáticamente. Esta versión
requiere 20261022120000_user_import_profile incluso para listar usuarios.
prisma/sql/auditoria_inmutable.sql es una opción de retención que TI debe evaluar
con su política: impide modificar o borrar auditorías existentes.

RESPALDOS DOCKER (EJEMPLO POWERSHELL)
Respaldar ambos volúmenes, no solo el código. Conservar fuera del servidor y cifrar
según la política de TI. Estos comandos no borran ni restauran datos:
  New-Item -ItemType Directory -Force backups | Out-Null
  $backupStamp = Get-Date -Format 'yyyyMMdd-HHmmss'
  docker compose --env-file .env.production -f docker-compose.production.yml exec -T postgres pg_dump -U seguridad_operativa -d seguridad_operativa -Fc -f /tmp/seguridad_operativa.dump
  docker compose --env-file .env.production -f docker-compose.production.yml cp postgres:/tmp/seguridad_operativa.dump "backups/db-$backupStamp.dump"
  docker compose --env-file .env.production -f docker-compose.production.yml exec -T backend tar -czf /tmp/uploads.tar.gz -C /app uploads
  docker compose --env-file .env.production -f docker-compose.production.yml cp backend:/tmp/uploads.tar.gz "backups/uploads-$backupStamp.tar.gz"
La restauración debe ensayarse en otro entorno, sin reemplazar la base activa.

IMPORTACIONES E INDICADORES
Usuarios: Admin > Gestión de Usuarios > Importar desde Excel. Se leen únicamente
las seis columnas autorizadas; puesto y unidad organizativa no otorgan permisos.
Elegir roles primero. Solo Jefe de Área requiere área, también en alta manual
y edición. Seguridad Operativa, Monitorista, Contingencias y Admin no tienen área.
Revisar el lote antes de confirmar: validar no crea cuentas. Las cuentas existentes
no se modifican. Descargar los accesos temporales al terminar y entregar cada
credencial solo a su titular; no se envían correos de alta automáticamente.
Cada persona debe cambiar su contraseña al primer ingreso. Probar este circuito
con cuentas de ensayo antes de importar personal real.
Los formularios, pasos, filtros y adjuntos seleccionados conservan borradores
en el navegador de la misma pestaña y cuenta durante un máximo de 24 horas.
Recargar recupera el avance; no equivale a guardar en el servidor ni reenvía
operaciones. Cerrar sesión limpia los borradores de esa pestaña. Borrar datos
del navegador o trabajar en otro dispositivo no permite recuperar ese avance.
Las contraseñas y los accesos temporales descargables no se guardan como
borradores. Descargar los accesos del lote antes de salir de su pantalla.
Después de recargar una importación, validar otra vez antes de confirmar. Si
se inició una carga, revisar usuarios o historial: recargar no cancela al servidor.
Si el navegador impide guardar borradores, la web muestra una advertencia y pide
guardar antes de recargar. Los borradores no reemplazan el respaldo de la base.
Monitoreo y Contingencias aceptan registros sin identificador externo: cada fila
válida se guarda por separado, aunque coincida con otra. Reimportar crea registros
adicionales. SOP mantiene sus controles por códigos y estados.
Elegir la hoja de datos, validar, revisar el diagnóstico y confirmar una vez.
Las fechas, horas, catálogos y límites de campos siguen siendo obligatorios.
Si se pierde la conexión, consultar el historial antes de repetir la carga.
Los indicadores consultan los eventos persistidos, incluyendo los importados,
por fecha y clasificación. Revertir una carga también modifica sus indicadores.
Monitoreo requiere km comerciales y pasajeros para sus índices.
Contingencias distingue Accidentes y Problemas de salud; tipos distintos aparecen
sin clasificar. Su tasa mensual requiere afluencia completa y clasificación válida.
No completar divisores desconocidos con valores inventados para obtener una tasa.
Se probaron XLSX de 3000 filas por módulo y guardado real en PostgreSQL de pruebas.
Los tiempos locales no garantizan los del servidor de la empresa.

VERIFICACIÓN

  copiar .env.test.example a .env.test y completar sus valores privados

El último comando prueba la compilación estática, además del servidor de desarrollo.

La regresión del lector también incluye una muestra sintética fija, sin datos reales.
Comprobar /api/health, acceso por roles, una carga controlada con sus indicadores,
Google, correo recibido y push en el dominio definitivo antes de habilitarlo.
TI debe verificar imágenes, HTTPS, capacidad, restauración y políticas de acceso
en su infraestructura. Las imágenes Docker no se ejecutaron en esta revisión
porque el motor Docker local no estaba disponible; se verificó la sintaxis compose.

ACEPTACIÓN ANTES DE HABILITAR PERSONAL
Probar con un representante de cada perfil: Admin, Seguridad Operativa, Jefe de
Área, Monitorista y Gestión de Planes de Contingencia. Confirmar qué tareas y
datos ve cada uno, y que no accede a paneles ajenos pegando sus direcciones.
Hacer un ciclo de reporte, evaluación/investigación, plan, ejecución y cierre con
datos de ensayo. Confirmar correcciones, pedidos de información, avisos, plazos,
riesgo y auditoría con el responsable funcional, no solo con el desarrollador.
Probar restauración de base y adjuntos, y asignar un responsable de respaldos y
supervisión de disponibilidad. No basta con que /api/health responda una vez.
Un fallo de carga ofrece recargar o volver al inicio. Si hubo un guardado en curso,
verificar primero el resultado antes de repetirlo. Escalar con pantalla y hora.
El soporte de TI debe conservar accesos a infraestructura y gestión de cuentas;
la operación no puede depender exclusivamente de la cuenta del desarrollador.
